## 공유 플러그인 실행 경로

이 문서가 들어 있는 `skills`의 상위 폴더를 `PLUGIN_ROOT`로 확인하고, 먼저 `../../references/recipient-runtime.md`를 읽는다. `${PLUGIN_ROOT}`는 현재 설치된 이 플러그인의 절대 경로로, `${VIDEO_PRODUCT_LIBRARY_ROOT}`와 `${CAPCUT_AUTOMATION_ROOT}`는 수신자 환경의 경로로 해석한다. 하위 스킬은 이 플러그인 안의 형제 폴더를 우선 사용한다. 플러그인 제작·수정·공유 요청은 영상 제작 인터뷰나 유료 생성, 앱 종료를 시작하지 않는다.


# 제품 맞춤 대본 작성

## 레퍼런스 구조 고정과 대본 컨펌

- 새 대본과 재작성 대본은 항상 레퍼런스 영상의 전체 대본을 먼저 확보한 뒤 작성한다. 모든 원문 문장·의미 단위에 순서 ID를 붙이고 `reference_structure_map`에 원문, 설득 역할, 위치, 대응 신규 문장, 제품 논리 근거를 1대1로 기록한다. 단순 문장 수 일치나 비슷한 분위기만으로 통과하지 않는다.
- 후킹, 반문, 정보 공개 순서, 제품 공개 위치, 원리·근거·혜택·CTA 위치, 문단, 표현 강도와 낭독 호흡은 레퍼런스 그대로 유지한다. 그 자리 안의 내용과 인과관계만 광고할 제품의 논리에 맞춘다. 과거 대본은 제품 논리의 출처이며 새 레퍼런스의 순서를 바꾸는 근거가 아니다. 일반 광고 공식으로 새 개요를 만들거나 기본 30~40초에 맞춰 임의 삭제·재배열하지 않는다. 실제 충돌이 있으면 해당 문장과 제품 논리의 충돌만 사용자에게 확인한다.
- 대본 전체를 출력한 뒤 반드시 명시적인 사용자 컨펌을 기다린다. 전체 제작·자동모드·편집 위임은 대본 승인이 아니다. 컨펌 전에는 화면 기획, 프롬프트, 이미지·영상·영상 내 음성·별도 TTS 생성, CapCut 편집을 진행하지 않는다. 승인 원문·시각과 대본 파일 SHA-256을 기록한다. 수정하면 기존 승인은 무효이며 전체 수정 대본을 다시 보여주고 컨펌받는다.
- 대본 출력 뒤의 짧은 컨펌 요청은 아래 출력 제한의 예외다. 제품 확인 질문에 대한 답이나 침묵을 전체 대본 컨펌으로 해석하지 않는다.

## 핵심 원칙

- `${VIDEO_PRODUCT_LIBRARY_ROOT}/<업체명>/_knowledge/products/<제품명>/product_context.md`를 기본 제품 정보원으로 사용하라. 이 파일이 사용자가 말한 `제품별 자산`이며, 업체 공용 요약이나 대화 세션의 막연한 기억으로 대체하지 마라. 사용자가 제품 지식 파일, 첨부 문서 또는 상세페이지 URL을 직접 지정하면 그 자료를 현재 작업의 추가 정보원으로 사용하라.
- 제품별 자산과 원본 제품 폴더는 읽기만 하라. 사용자가 제품 지식 추가·갱신·정리를 별도로 요청한 경우에만 `extract-product-ad-knowledge` 스킬 또는 해당 자산 갱신 워크플로를 사용하라.
- 새 대본을 쓰기 전에 같은 업체·같은 제품의 최근 승인 대본과 실제 영상 편집에 사용된 대본을 반드시 조회하라. 여기서 추출한 `prior_video_logic`이 제품의 문제 → 원인 → 기존 해결책의 한계 → 제품 원리 → 기대 결과 → 근거/혜택 → CTA 논리 골격이다. 새 레퍼런스는 이 골격을 버리고 전혀 다른 제품 논리를 만드는 자료가 아니라, 문장별 설득 역할·표현 강도·정보 공개 방식·리듬을 입히는 표현 자료다.
- 이전 대본 조회는 모든 업체와 제품에 공통 적용하되, Unicode·대소문자·연속 공백만 정규화한 정확한 업체/제품 범위 안에서만 수행하라. 같은 업체의 다른 제품, 비슷한 제품명, 다른 업체 대본, 업체 공용 대본을 절대 섞지 마라.
- 레퍼런스의 문장별 설득 역할, 문장 수, 문단, 정보 공개 순서, 표현 강도, 길이와 리듬을 순서와 역할을 그대로 1대1로 유지하라. 단어와 제품 사실은 선택 제품에 맞게 전부 새로 작성하라.
- 검증 모드에서는 레퍼런스의 업체명, 제품명, 고유 문구, 가격, 혜택, 효능, 후기, 근거와 수치를 새 대본에 옮기지 마라. 미검증 컨셉 초안 모드에서는 업체명·제품명만 신규 제품으로 바꾸고, 레퍼런스의 수치·근거·효능·경력·혜택은 같은 설득 기능을 수행하는 임시 컨셉 문장으로 치환할 수 있다.
- 검증 모드에서는 선택한 업체와 제품의 조회 결과에 없는 사실을 만들지 마라. 구조 충실도와 사실성이 충돌하면 사실성을 우선하되, 문장을 삭제하기 전에 같은 설득 기능을 수행할 수 있는 다른 확인 사실이나 비사실성 연결 문장으로 치환하라.
- 업체 또는 제품의 금지 표현과 근거 규칙을 레퍼런스의 자극 강도보다 우선하라.

## 작성 모드 선택

다음 기준으로 모드를 선택하라.

1. **미검증 컨셉 초안 모드**를 기본값으로 사용하라. 별도 모드 요청이 없어도 이 모드로 작성하라.
2. 사용자가 `검증 모드`, `확인된 사실만`, `근거 있는 문구만`, `집행 가능한 대본`, `허가 범위만`처럼 사실성 검증을 명시하면 **검증 모드**로 전환하라.

미검증 컨셉 초안 모드에서는 다음을 지켜라.

- 사용자가 직접 제시한 효과 배수, 개선 기간, 효능, 인증, 비교, 가격, 환불 문구를 사실 검증 없이 초안 안에 그대로 사용할 수 있다.
- 사용자가 신규 문구를 따로 주지 않은 문장은 레퍼런스의 수치·기간·효능·인증·전문가 경력·가격·환불 구조를 신규 제품 문맥에 맞는 임시 컨셉으로 완성하라. 자리표시자를 남기지 마라.
- 모든 미검증 문구는 게시 가능한 사실로 단정해 설명하지 말고, 첫 줄의 내부 편집용 표시 아래에서만 완성형 광고 문장으로 제시하라.
- 첫 줄에 `※ 내부 편집용 미검증 컨셉 초안 — 수치·기간·효능·인증·혜택은 게시 전 교체 또는 확인 필요`를 한 번만 표시하라.
- 위 표시 외에는 분석, 근거 설명, 경고 목록과 검수 메모를 붙이지 마라.

미검증 컨셉 초안은 의심 정보를 자동 승인하는 모드가 아니다. 제품별 자산과 레퍼런스를 대조하고, 다음 중 하나가 대본의 핵심을 실질적으로 바꾸더라도 먼저 완성형 초안을 작성한 뒤 그 아래에 최대 세 가지의 짧고 구체적인 확인 질문을 붙여라.

- 제품명·옵션·패키지·제품 유형·섭취 또는 사용법이 서로 충돌한다.
- 핵심 성분, 작동 원리, 타깃 니즈 또는 사용 대상이 모호하거나 서로 다른 자료에서 불일치한다.
- 가격·혜택·기간·수치·인증·효능 주장이 제품별 자산의 `확인 필요`, `동적 정보`, `사용 금지`와 직접 충돌하거나 위험한 오인 가능성이 있다.
- 레퍼런스의 핵심 설득 문장을 신규 제품에 옮기면 제품 정체성을 잘못 설명하게 된다.

단순히 검증 근거가 없다는 이유만으로 임시 컨셉 문장마다 질문하지 마라. 제품별 자산과 충돌하지 않는 의도적 미검증 수치·기간·효능·혜택은 내부 초안 표시 아래에서 작성한다. 확인 질문은 대본을 막는 사전 게이트가 아니며, 초안에서 실제로 사용한 의심 문구의 유지·교체 여부만 묻는다. 사용자가 답하면 그 답을 현재 초안의 기획 입력으로만 반영하고 게시 가능한 검증 사실로 승격하지 마라.

## 실행 절차

### 1. 세 가지 입력을 인터뷰하라

최종 대본을 작성하기 전에 다음 값을 확보하라.

1. 업체명
2. 제품명
3. 레퍼런스 대본

아무 값도 없으면 한 번의 짧은 질문으로 세 항목을 요청하라. 이미 받은 값은 다시 묻지 말고 누락된 값만 질문하라. 레퍼런스 대본은 채팅에 붙여 넣은 텍스트, 첨부 파일 또는 읽을 수 있는 로컬 파일 경로로 받을 수 있다. 첨부 파일이나 경로라면 내용을 읽어 실제 대본 텍스트를 확보하라.

업체명과 제품명을 모두 받기 전에는 임의 제품을 선택하지 마라. 레퍼런스 대본을 받기 전에는 일반적인 플로우를 대신 사용하지 마라. 사용자가 낭독 시간을 따로 지정하면 함께 기록하라. 지정하지 않으면 레퍼런스 전체 구조와 낭독 분량을 유지하라. 지정 시간과 구조 보존이 양립하지 않으면 임의 축약하지 말고 충돌을 확인하라.

### 2. 제품별 자산을 조회하라

기본 루트와 1차 자산은 다음 경로로 고정하라.

```text
${VIDEO_PRODUCT_LIBRARY_ROOT}
${VIDEO_PRODUCT_LIBRARY_ROOT}/<업체명>/_knowledge/products/<제품명>/product_context.md
```

1. 루트 바로 아래에서 업체명과 정확히 일치하는 폴더를 찾는다.
2. 해당 업체의 `_knowledge/products` 바로 아래에서 제품명과 정확히 일치하는 폴더를 찾는다.
3. 그 폴더의 `product_context.md`를 처음부터 끝까지 읽는다. 이 집약 자산의 제품 지식, 타깃 니즈, 이미지·제품 특징, 승인된 개선 규칙, 부정 예시와 최근 대본 이력의 상태 구분을 유지한다.
4. `product_context.md`가 없을 때만 정확한 `${VIDEO_PRODUCT_LIBRARY_ROOT}/<업체명>/<제품명>/제품 정보/` 폴더를 찾아 `product-ad-knowledge.md`, `product-assets.json`, `product-visual-source-pack.md`를 순서대로 조회한다.
5. 제품별 자산이 원본 제품 정보 파일을 가리키면 필요한 원본을 읽어 충돌 여부와 현재성을 확인한다.

상위 스킬이 같은 실행 안에서 정확한 `product_context.md` 경로와 그 전체 내용을 이미 제공했다면 파일이 변경되지 않았음을 확인하고 해당 컨텍스트를 재사용하라. 동일 파일을 불필요하게 두 번 읽지 마라.

- 업체명과 제품명은 Unicode, 대소문자, 연속 공백만 정규화해 정확히 일치시켜라. 후보가 하나뿐이어도 부분 일치나 폴더명 추측으로 자동 선택하지 마라.
- 제품명이 없는 업체 공용 프로젝트, 날짜형 작업 폴더, 생성 결과물, 다른 제품 폴더를 제품 지식으로 사용하지 마라.
- 정확한 폴더가 없으면 실제 폴더 후보만 보여주고 사용자의 정확한 선택을 요청하라.
- `product_context.md`와 원본 제품 정보 파일이 모두 없으면 임의로 기존 영상 문구를 사실처럼 사용하지 마라. 사용자가 상세페이지 URL이나 자료를 제공했다면 `extract-product-ad-knowledge`로 지식을 먼저 정리하고, 자료가 없으면 제품 정보원을 요청하라.
- 현재 제품 폴더에서 읽은 사실만 생성 컨텍스트에 사용하라. 같은 업체의 다른 제품이나 다른 업체의 사실을 섞지 마라.
- 문서의 `확인된 사실`, `페이지 주장`, `동적 정보`, `광고 해석`, `확인 필요`를 구분해 유지하라. 검증 모드에서 동적 가격·혜택·재고·후기·배송을 사용하려면 문서의 확인일이 현재 집행 시점과 다를 때 원문을 다시 확인하라.
- `product-assets.json`에서 `approved_current_packaging`, `approved_factual_reference`, `approved_visual_reference`로 표시된 자산만 승인 범위에 맞게 사용하라. `candidate`, `concept_reference_only`, `verify_first` 자산을 사실 근거나 공식 제품 마스터로 승격하지 마라.

### 3. 이전 영상 대본의 제품 논리를 고정하라

[이전 영상 대본 논리 계승 절차](references/prior-video-script-logic.md)를 처음부터 끝까지 읽고 적용하라. 다음 읽기 전용 도구를 먼저 실행한다.

```bash
python3 scripts/prior_video_script_logic.py --company "<업체명>" --product "<제품명>"
```

1. 도구가 반환한 상위 `selected_sources`를 모두 처음부터 끝까지 읽는다. 같은 내용의 낭독용 변환본, TTS 조각, CTA 보충 조각은 중복 근거로 세지 않는다.
2. `product_context.md`의 `승인된 최근 대본 예시`와 도구가 찾은 최신 승인본·CapCut 실사용 입력본을 우선한다. 단순 미승인 초안이나 생성 중간본은 승인본이 없을 때만 보조 자료로 사용한다.
3. 내부 `prior_video_logic`에 최소한 `hook`, `problem`, `cause`, `existing_solution_limit`, `product_reveal`, `mechanism`, `result`, `proof_or_offer`, `cta`, `must_preserve`, `superseded`를 기록한다. 각 항목은 실제 읽은 출처 경로와 SHA-256으로 추적 가능해야 한다.
4. 최신 사용자 직접 정정과 현재 `product_context.md`의 승인된 개선 규칙이 이전 대본보다 우선한다. 이전 대본의 가격·재고·할인·후기·혜택은 현재 사실로 승격하지 않는다.
5. `status: no_prior_video_script`이면 현재 제품 컨텍스트만으로 진행한다. 이때 다른 업체나 제품에서 논리를 빌리지 말고, 이전 대본이 없다는 이유만으로 사용자의 입력을 다시 묻지 마라.

`prior_video_logic`을 만들기 전에는 초안을 작성하지 마라. 사용자가 명시적으로 새 논리나 새 소구를 요청한 경우에만 해당 범위에서 바꾸고, 무엇이 바뀌었는지는 내부적으로 기록한다.

### 4. 사용자 지정 작성 지침을 적용하라

[숏폼 퍼포먼스 광고 재구성 지침](references/script-flow.md)을 전부 읽고 최상위 작성 계약으로 적용하라.

레퍼런스를 문장 또는 의미 단위로 나누고 각 단위의 역할과 연결 논리를 내부적으로 분석하라. 분석 내용, 역할 라벨, 매핑표와 검수 과정은 사용자에게 보여주지 마라.

### 5. 문장 단위로 1대1 치환하라

레퍼런스의 각 문장을 같은 위치와 설득 기능을 가진 신규 문장으로 치환하되, 제품의 인과관계와 설득 결론은 `prior_video_logic`을 기본값으로 사용하라. 기존 제품 논리를 레퍼런스의 각 원래 위치에 맞는 설명으로 재작성하라. 레퍼런스의 문장 순서를 기존 대본 순서로 옮기거나 전혀 새로운 제품 원인·원리·CTA를 만들지 마라. 같은 자리에서 해결할 수 없는 실제 충돌만 사용자에게 확인하라.

검증 모드에서는 다음 우선순위를 지켜라.

1. 업체·제품 금지 표현과 근거 규칙
2. 신규 제품의 사실성
3. 업체·제품 필수 문구
4. 레퍼런스의 문장별 설득 역할과 정보 공개 순서
5. 레퍼런스의 자극 강도, 말투, 길이와 낭독 리듬

대응 정보가 없으면 그 문장을 즉시 삭제하지 마라. 같은 설득 기능을 수행할 수 있는 다른 검증 사실로 먼저 대체하고, 그것도 불가능하면 새 사실을 주장하지 않는 반문·전환·강조 문장으로 해당 위치를 유지하라. 허위 수치나 효능을 만들어서 문장 수를 맞추지 마라.

미검증 컨셉 초안 모드에서는 `사용자가 직접 제시한 가설 주장 → 레퍼런스의 문장별 역할과 임시 수치·근거 → 제품명과 제품 작동 원리` 순서로 치환하라. 사용자가 준 `10배`, `2주`, `싹 회복` 같은 문구는 순화하거나 삭제하지 말고 같은 위치와 강도로 사용하라. 사용자가 별도 값을 주지 않은 문장도 자리표시자 없이 레퍼런스와 같은 완성도로 작성하라.

### 6. 내부 검수 후 대본을 먼저 출력하라

작성 지침의 `6단계: 결과물 점검`을 모두 통과할 때까지 내부적으로 수정하라. 실제 낭독 분량도 확인해 사용자가 지정한 시간 또는 레퍼런스의 전체 낭독 분량을 기준으로 하라. 레퍼런스의 구조 보존이 우선이며 충돌은 임의 축약으로 해결하지 마라.

성공한 최종 출력에는 다음 규칙을 적용하라.

- 검증 모드에서는 완성된 광고 대본만 출력하라.
- 미검증 컨셉 초안 모드에서는 지정된 내부 초안 표시 한 줄과 광고 대본을 먼저 출력하라.
- 의심 정보가 있으면 대본 뒤에 빈 줄을 두고 `확인 질문`을 적은 다음, 초안에 실제 사용한 문구에 관한 질문을 최대 세 개까지 번호로 붙여라. 의심 정보가 없으면 이 구역을 생략하라.
- 확인 질문 외에는 분석, 설명, 주의사항, 작성 의도, 적용 플로우와 검수 메모를 출력하지 마라.
- 대본에는 제목, Markdown 헤더, 글머리표, 인용문, 코드 블록과 writing block을 붙이지 마라. `확인 질문` 구역의 번호 목록만 예외로 허용한다.
- 레퍼런스와 같은 문단 형식을 유지하라.
- 같은 업체·제품의 `prior_video_logic`이 대본의 문제·원인·기존 해결책 한계·제품 원리·결과·CTA에 실제로 반영됐는지 확인하라. 단순히 제품명이나 성분만 재사용한 것은 논리 계승이 아니다.

입력 누락, 업체·제품 폴더 불일치 또는 제품 지식 문서 누락처럼 대본 자체를 작성할 수 없는 경우에만 사전 질문이나 오류 안내만 출력하라.
